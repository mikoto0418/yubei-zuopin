# ScriptForge 设计说明

> 剧本 / 长篇小说创作工作台 · 端口 4204 · Express + Vue 3 + Arco Design Vue

---

## 一、为什么是「纸张质感 + 衬线正文」

`APPLE_DESIGN_SYSTEM.md` 要求十个产品共享同一套设计基底，每套只在一个维度上做差异化。
ScriptForge 分到的差异化维度是 **纸张质感 + 衬线正文**。这不是装饰，而是由这个产品的
使用场景决定的：

### 1. 写作是长时间、高密度的阅读行为

界面元素（按钮、导航、表单）是**点一下就离开**的，用无衬线最快、最清晰 —— 所以它们
严格保持 Apple 基底的无衬线字体。

但场景正文不一样。编剧和小说作者会盯着同一段文字**连续读写数小时**：

- **衬线的字形对比更柔和。** 无衬线（尤其 PingFang / 微软雅黑）的字面率高、笔画均匀，
  在 17px 这个正文尺寸上长时间阅读会产生「字挤在一起」的压迫感。宋体一类的衬线有
  明显的横细竖粗与起收笔，眼睛靠字形轮廓就能分辨字与字，减少了逐字识别的负担。
- **中文排版传统上正文就是宋体。** 剧本和小说是「文本作品」，读者对"正文 = 宋体"有
  稳定的预期。这个预期让工具显得**像稿纸而不是像后台管理系统**。

### 2. 米色纸降低屏幕眩光

编辑器底色取 `#FBF9F6`（米色纸），而不是纯白：

- 纯白 `#FFFFFF` 在室内照明下反射率高，长时间盯着容易视疲劳；
- 米色把色温往暖侧偏了一点，**降低对比强度但保持正文对比度 ≥ 4.5:1**（墨色 `#23201C`
  对米色 `#FBF9F6` 的对比度约为 14:1，远高于无障碍下限）；
- 纸张左侧留了一道 4px 的浅色「装订线」，加一条极淡的稿纸横线背景，把「这是一张纸」
  的隐喻做足 —— 但**不加阴影、不加纹理图片**，避免变成拟物化。

### 3. 深色模式仍然保留"纸"的观感

深色下纸张转为深米色 `#1E1B18`（不是纯黑），墨色转为 `rgba(240,235,226,0.92)`。
关键点是**不换成"黑底白字的终端"**：如果深色模式把纸张变成 `#000`、正文变成纯白，
那这个产品在夜间就退化成了普通的代码编辑器，差异化维度就丢了。

### 4. 差异化的边界（严格遵守 Apple 规范的部分）

差异化**只作用于内容阅读区**，以下全部保持 Apple 基底：

| 区域 | 字体 | 底色 |
|---|---|---|
| 场景正文编辑器 | **衬线 17px / 行高 1.8** | **米色纸 `#FBF9F6`** |
| 对白台词展示 | 衬线（与正文一致，属内容区） | 跟随卡片 |
| 版本对比中的正文差异 | 衬线 | 跟随卡片 |
| 按钮 / 表单 / 导航 / 表格 / 徽章 | 无衬线 | 遵循基底 |
| 卡片 / 圆角 / 阴影 / 间距 / 动效 | 完全不改 | 遵循基底 |

字号阶梯、圆角档位、阴影两档、间距 8px 栅格、动效曲线 —— **一个都没有改**。
这是「同一位设计师做的不同 App」而不是「十个年代的产品」的关键。

## 三、数据模型（12 张表）

| 表 | 说明 |
|---|---|
| `users` | 账号，角色 admin / writer / editor |
| `projects` | 作品：类型、题材、logline、梗概、状态 |
| `episodes` | 分集 / 章节，归属作品，有序 |
| `scenes` | 场景：地点、时间、正文、状态、字数 |
| `characters` | 角色卡：姓名、年龄、身份、性格、目标、弧光 |
| `character_relations` | 角色关系（有向）：父子 / 恋人 / 敌对 / 师徒… |
| `scene_characters` | 场景出场角色（多对多，支撑逻辑检查） |
| `dialogues` | 对白：角色 + 台词 + 情绪提示 |
| `storylines` | 故事线：A/B/C 线，主线 / 支线 |
| `storyline_scenes` | 故事线关联场景（多对多） |
| `notes` | 创作笔记：灵感 / 设定 / 参考 / 待办 |
| `revisions` | 场景版本快照（JSON 快照 + 版本号） |

**关键设计取舍**

- **场景挂在分集下，作品 id 由分集推导。** 前端创建场景只需传 `episode_id`，
  后端 `crud.js` 的 `derive` 钩子自动补 `project_id`，避免前端拼错关联。
- **字数由后端计算。** 场景保存后 `afterWrite` 钩子重算 `word_count`，
  不接受前端传入 —— 字数是一个派生事实，不是用户输入。
- **快照存整行 JSON。** 回滚时按字段逐个写回，简单且不会漏字段；
  对比时只取 5 个业务字段做 diff，不把 `updated_at` 之类的噪音算进差异。

## 四、状态机

### 作品（5 状态）

```
draft（草稿）
  → reviewing（送审）      ← 编剧自己提交
  → revising（返修）        ← 责编打回
  → approved（过审）        ← 责编通过
  → archived（归档）
```

允许的流转（后端 `PROJECT_FLOW` 校验，非法流转返回 400）：

| from | to |
|---|---|
| draft | reviewing, archived |
| reviewing | revising, approved, draft |
| revising | reviewing, approved, draft |
| approved | archived, revising |
| archived | draft |

**权限边界**：`approved` 与 `revising` 是**审阅动作**，只有 editor / admin 能做；
`reviewing`（送审）是编剧自己的动作。这样设计的原因是：让"过审"成为一个
不可由作者自证的结论 —— 这正是责编这个角色存在的意义。

### 场景（4 状态）

```
outline（大纲）→ drafted（初稿）→ revised（修订）→ final（定稿）
```

允许**相邻回退**（`drafted → outline`、`revised → drafted`、`final → revised`），
但不允许跨级跳跃（`final` 不能直接回 `outline`）—— 写作是迭代的，
回退一步是常态，推翻重来应该走「新建场景」而不是篡改状态。

## 五、权限模型

三种角色，读写权限**分离**：

| 角色 | 读 | 写 |
|---|---|---|
| `admin` | 全部 | 全部 |
| `editor`（责编） | **全部作品**（审阅需要） | 只有自己的 |
| `writer`（编剧） | 只有自己的 | 只有自己的 |

这条"editor 可读全部但只能写自己的"是本项目的核心权限设计：

- 责编**必须能读**所有作品才能审阅 —— 所以列表查询的归属过滤对 editor 放行；
- 但责编**不能替编剧改稿** —— 所以 `canWrite` 里 editor 不被放行。
- 审阅意见通过 `notes` 表传递（返修意见写成 `kind='todo'` 的待办），
  编剧端在「创作笔记」页看到并逐条勾掉 —— **审阅结果驱动后续修改流程**。

实现上，`access.js` 导出 `canRead(row, user)` / `canWrite(row, user)`，
参数顺序统一为 `(row, user)`，与 `crud.js` 的调用约定一致。

## 六、AI 功能（4 个，含落库）

所有 AI 路由统一走内核的 `ai.generate(messages, buildLocal)`：
未配置 `LLM_API_KEY` 时**自动降级为本地规则**，响应体带 `source` 字段（`llm` / `local`），
前端在结果抽屉里明确标注「引擎：大模型 / 本地规则（未配置 Key 自动降级）」。

| 接口 | 功能 | 是否落库 |
|---|---|---|
| `POST /api/ai/character-gen` | 根据身份描述生成完整角色卡 | **写入 `characters` 表** |
| `POST /api/ai/polish-dialogue` | 对白润色，保留角色语气 | 返回建议，由作者决定是否采用 |
| `POST /api/ai/plot-suggest` | 基于故事线给冲突 / 转折建议 | 返回建议 |
| `POST /api/ai/logic-check` | 检查场景间时间 / 地点 / 角色矛盾 | **写入 `notes` 表作为待办** |

**两个落库闭环**

1. **角色生成 → 角色表 → 关系图。** AI 生成的角色立即出现在角色卡网格和 SVG
   关系图节点里，可以马上给它连关系、分配出场场景。
2. **逻辑检查 → 创作笔记待办 → 逐条勾掉。** 检查结果不是一次性弹窗，而是变成
   `kind='todo'`、`source='ai'` 的笔记。作者修完一场就勾掉一条；
   同场景已有未处理待办时跳过，避免反复检查堆出重复项。

本地降级规则引擎实现了三类检查：
- 相邻两场时段相同却换地点 → 提示确认转场是否交代；
- 角色间隔 6 场以上才再次出场 → 提示补一句去向；
- 场景未配置出场角色 → 提示对白无法归属说话人。

## 七、前端结构

### 页面（11 个，全部五态齐全）

| 路由 | 页面 | 说明 |
|---|---|---|
| `/login` | 登录 / 注册 | 分段控件切换，演示账号一键填入 |
| `/projects` | 作品列表 | 卡片网格（封面 / 类型 / 题材 / 状态徽章 / logline） |
| `/studio/:id` | **创作工作台** | 三栏：结构树 / 场景编辑器 / 角色速查 + 故事线 |
| `/characters` | 角色管理 | 角色卡网格 + SVG 手绘关系图 |
| `/dialogues` | 对白编辑 | 结构化列表 + 导出标准剧本格式 |
| `/storylines` | 故事线 | A/B/C 线 + 关联场景 + 完整性检查 |
| `/revisions` | 版本历史 | 快照列表 + 逐字段对比 + 回滚 |
| `/notes` | 创作笔记 | 灵感 / 设定 / 参考 / 待办，可标记完成 |
| `/review` | 审阅台 | 待审队列 + 通过 / 返修（editor / admin） |
| `/admin` | 管理概览 | 13 项业务指标 + 账号表（admin） |
| `/403` `/404` | 无权限 / 不存在 | 带返回入口 |

### 五态实现

统一的 `StateBlock.vue` 组件承载四种非就绪态：

- **加载态**：骨架屏（Apple 规范要求用骨架不用转圈）；
- **空态**：插图 + 一句说明 + 一个行动按钮；
- **错误态**：说明 + 重试按钮；
- **无权限态**：锁图标 + 说明；
- 就绪时渲染 `slot`。

### 创作工作台（核心页）

三栏布局，各自独立滚动：

- **左栏**：作品结构树（分集可折叠 → 场景列表，带场景状态徽章）；
- **中栏**：场景编辑器 —— 标题、地点、时间、出场角色，以及**米色纸 + 衬线正文的编辑区**，
  下方是本场对白列表；右上角是场景状态流转下拉和「保存快照」；
- **右栏**：角色速查（头像字 + 身份）与故事线列表。

顶栏是作品状态流转下拉（只列出合法流转目标）与两个 AI 入口。

### 状态徽章

`StatusBadge.vue` 按 `kind`（project / scene / note）渲染不同标签，
配色走 Apple 语义色（送审=橙、返修=红、过审=绿、定稿=绿、初稿=靛），
深色模式下单独调过前景色保证对比度。

本目录此前是一个"知识库文档"系统（spaces / docs / revisions）。本次按
`FUNCTIONAL_SPEC.md` §3.2 的要求**完全重写为剧本 / 小说创作工作台**：

## 九、已知边界

- 分集 / 场景的拖拽排序在数据层已有序号字段（`seq`），前端目前通过"新增时追加到末尾
   + 手动填序号"实现顺序调整，未做拖拽交互。
- 角色头像使用姓名首字生成的色块，未接入图片上传（`avatar` 字段已预留）。
- AI 降级规则引擎是启发式的，覆盖三类常见矛盾，不追求完备。
